# Lightning.Pub — Architecture (Contributor Guide)

> How the codebase is shaped so changes land in the right place and stay easy to review.  
> This is **not** a product/feature walkthrough (payments, liquidity, etc.) — those belong in feature docs or PRs.

## What this is (one sentence)

A **Nostr-native RPC + account layer on LND**, built as **class-centric encapsulation**: domain managers own collaborators injected at construction; transports stay thin; persistence stays behind storage facades.

---

## Mental model

```
API contract (proto)
        ↓
Transport adapters (serverMethods, nostrMiddleware, auth)
        ↓
Main (composition root — owns managers, LND callbacks)
        ↓
Domain managers (business rules, orchestration)
        ↓
Infrastructure (Storage / LND / Nostr / helpers)
```

**Rule of thumb:** if a reviewer has to jump more than one layer to understand *why* a change exists, the responsibility probably landed in the wrong file.

| Layer | Lives in | Owns | Must not own |
|---|---|---|---|
| Contract | `proto/service/` | Request/response shapes, auth roles | Logic |
| Transport | `src/services/serverMethods/`, `src/auth.ts`, `src/nostrMiddleware.ts` | Validate + auth context + dispatch | Business rules, DB, LND |
| Composition | `src/services/main/index.ts`, `src/services/main/init.ts` | Wiring, boot, LND→domain callbacks | Feature logic dumps |
| Domain | `src/services/main/*Manager.ts` (and peers) | Use-cases for one vertical | Raw SQL/TypeORM, gRPC or Nostr wire details |
| Persistence | `src/services/storage/*Storage.ts`, `entity/`, migrations | CRUD, tx helpers, invariants of rows | RPC shapes, Lightning policy |
| Lightning I/O | `src/services/lnd/` | gRPC, streams, decode/pay/invoice helpers | User balances, app fees |
| Cross-cutting | `src/services/helpers/` (incl. `Utils`), `src/services/metrics/` | Logging, TLV metrics, Nostr send attach, safe fetch, `MetricsManager` | Domain decisions |

## Boot & composition (where new objects get wired)

```
src/index.ts
  ├─ initSettings()       → Storage + SettingsManager
  └─ initMainHandler()    → Unlocker, Swaps, AdminManager, optional Wizard,
                            Main, LND warmup, sanity, default app keys,
                            recovery hooks, Watchdog
        ├─ GetServerMethods(mainHandler)
        ├─ nostrMiddleware(...)
        └─ NewServer(...).Listen(port)
```

**Ownership:** `Main` owns long-lived domain managers. `init.ts` may construct collaborators that must exist before `Main` (Unlocker, Storage/Settings, etc.) and is the only other wiring site.

When you add a new long-lived collaborator:

1. Create the class with **explicit constructor deps** (no service locator).
2. Instantiate it in **`Main`’s constructor** (or in `init.ts` if it must exist before `Main`).
3. Expose it as a field on `Main` only if transport or another manager needs it.
4. If it needs boot-time work (resume jobs, start loops), call that from **`initMainHandler`**, not from a random import side effect.
5. If it needs teardown, hook **`Main.Stop()`**.

Do **not** construct heavy managers ad-hoc inside RPC handlers.

## How to add a feature (happy path)

Prefer this sequence so PRs stay layered and reviewable:

1. **Proto** — add/adjust messages and RPC in `proto/service/` (`structs.proto`, `methods.proto`), including the right **auth** (`user` / `admin` / `app` / `guest` / …). Regenerate (`npm run build_autogenerated` / `gen`).
2. **Storage** (if needed) — entity + migration + method on the relevant `*Storage` class. Keep methods small and named after persistence intent (`AddProduct`, `IncrementUserBalance`, `getGrants`).
3. **Manager** — implement the use-case. Take `Storage` + only the peers you need. Return **proto types** (or throw). No transport knowledge (`ProductManager` is the tidy-slice template).
4. **`serverMethods`** — validate with generated `*Validate` helpers, then one call into the manager. No branching beyond “invalid → throw”.
5. **Wire** — if the manager is new, construct it on `Main`.
6. **Tests** — prefer exercising the manager (or bootstrapped `Main`) over inventing a parallel harness.

A change that needs proto + storage + manager + one `serverMethods` line is a **complete**, reviewable unit. Avoid “logic only in `serverMethods`” or “logic only in entity hooks”.

### Prefer a new manager over growing a god-object

`PaymentManager` is already the largest domain file. Default bias for new work: **new class in `src/services/main/`**, not another hundred lines on `PaymentManager` / `AdminManager` / `Main`, unless the change is clearly the same vertical.

## Transport habits

### Thin method tables stay boring

RPC pattern everywhere:

```ts
SomeRpc: async ({ ctx, req }) => {
  const err = Types.SomeRpcRequestValidate(req, { /* CustomChecks */ })
  if (err != null) throw new Error(err.message)
  return mainHandler.someManager.SomeMethod(ctx, req)
}
```

If a PR adds non-trivial `if` / loops / fee math here, push it down into a manager.

HTTP (generated Express) and Nostr RPC share `ServerMethods`. Auth differs (`src/auth.ts` vs Nostr guards in `src/nostrMiddleware.ts`), but **domain code must not care which transport called it**. Pass `ctx` + `req`; don’t inspect Express or Nostr types inside managers.

### Kind-based Nostr protocols (e.g. CLINK)

Protocols that use Nostr kinds instead of the generic `rpcName` table (e.g. `21001` / `21002` / `21003`) still follow the same layering: **middleware parses and routes; a thin methods adapter validates and dispatches; the manager takes `ctx` + `req` and returns a result**. Managers must not take `NostrEvent` or encode/send Nostr replies — that stays at the transport edge, same as RPC.

## Encapsulation & dependency rules

1. **Managers receive collaborators in the constructor.** They may call other managers they were given (e.g. `AppUserManager` → `ApplicationManager`), but they should not reach up into `Main` or import the process entrypoint.
2. **Thin method tables are the only places that treat `Main` as a bag of services** (acceptable service-locator at the edge) — `serverMethods` for RPC, and the same-style adapter for kind-based protocols.
3. **Persistence only through `Storage` / `*Storage`.** Managers never talk to TypeORM repositories or the DB subprocess protocol directly.
4. **Lightning only through `LND` (or injected swap/LSP helpers).** Don’t scatter gRPC client setup into domain managers.
5. **Settings through `SettingsManager.getSettings()`** (or storage settings accessors). Avoid new `process.env` reads deep in managers; put knobs in settings loaders so behavior is overrideable in tests (`OverrideTestSettings`).
6. **Callbacks for async node events live on `Main`.** LND streams invoke `addressPaidCb` / `invoicePaidCb` / `newBlockCb` / etc. Domain reactions are orchestrated there or delegated immediately to a manager. Don’t invent a second global event bus without a strong reason.

---

## Storage & transactions

- DB access is **out-of-process** (`StorageInterface` forks `storageProcessor`). Treat storage as an async API with optional `txId`, not as “we’re in the same TypeORM unit of work in-memory”.
- Multi-step money / consistency work: `storage.StartTransaction(async tx => { ... })` and **thread `tx` into every storage call** in that block.
- Balance mutations go through **`userStorage` increment/decrement** helpers (they also write the events log). Don’t `Update` balances ad-hoc in random managers.
- New tables: **entity + migration + `*Storage` methods**. Keep migration focused; don’t embed backfills in unrelated managers if a migration/init step is clearer.

---

## Errors, logging, side effects

- **Errors:** `throw new Error("clear message")` is the default; transports surface the message. Use dedicated error classes when callers must branch (see debit errors).
- **Logging:** `getLogger({ component: 'YourManager' })`, with `ERROR` / `INFO` / `DEBUG` symbols from `src/services/helpers/logger.ts`. Prefer component-scoped logs over anonymous `getLogger({})` inside new code.
- **Separate “commit” from “notify”:** e.g. credit in a transaction, then `PaymentSideEffects` / Nostr send. When adding outbound effects (HTTP callbacks, push, Nostr live ops), keep them **after** the durable state change and failure-tolerant where possible so retries don’t double-credit.

## Naming & file placement

| Kind | Convention | Location |
|---|---|---|
| Domain use-cases | `*Manager` | `src/services/main/` |
| Persistence | `*Storage` | `src/services/storage/` |
| ORM model | entity class | `src/services/storage/entity/` |
| Boot / wiring | `init.ts`, `Main` | `src/services/main/` |
| RPC / kind dispatch | thin method tables | `src/services/serverMethods/` |
| Metrics | `MetricsManager` | `src/services/metrics/` |
| Cross-cutting helpers | plain functions / small classes (`Utils` in `utilsWrapper.ts`) | `src/services/helpers/` |
| Process edge | auth, Nostr middleware, entry | `src/auth.ts`, `src/nostrMiddleware.ts`, `src/index.ts` |

Older code often uses **anonymous `export default class`**; newer managers use **named exports** (`DebitManager`, `OfferManager`). Prefer **named exports** for new classes — easier to grep and review.

## What makes a change easy to review

Checklist against the rules above — expect pushback when a diff breaks them:

- One vertical end-to-end (proto ↔ manager ↔ storage) with a thin transport line; behavior named like the RPC.
- Declarative `*Validate` / `CustomCheck`s; no fee math or business branching in method tables / middleware / `auth.ts`.
- No Express, Nostr wire types, TypeORM, or process forks inside managers; no ad-hoc balance `Update`s.
- No unrelated growth of `PaymentManager` / `Main`; no buried `process.env`; no hidden request-path singletons.
- Transactions / balance updates localized; side effects after commit and safe under retry; proto auth matches reachability.
- Tests call the same manager APIs production uses.

## Service map (orientation)

```
src/
  index.ts, auth.ts, nostrMiddleware.ts   # process edge
  services/
    main/           # Main + domain managers + init
    serverMethods/  # thin RPC / kind adapters
    storage/        # Storage facade, *Storage, entity, migrations, db subprocess, tlv
    lnd/            # LND wrapper, LSP, swaps
    nostr/          # relay pool / encryption / sender
    metrics/        # MetricsManager
    wizard/ ShockPush/ webRTC/ helpers/   # helpers includes Utils
proto/service/      # source of truth for RPC + structs
```
